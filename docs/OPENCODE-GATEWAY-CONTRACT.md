# عقد بوابة OpenCode

**الحالة:** مرحلي — واجهة الدردشة تستهلك حالياً كتالوج تفضيلات محلياً، ولا تدّعي اتصالاً بمحرك OpenCode قبل تحقق صحيّته واكتشاف نماذجه فعلياً.

## الغرض

تُبقي واجهة Osamah IDE اختيار النموذج مستقلاً عن محرك التشغيل. لا تصل الواجهة إلى مفاتيح المزودين، ولا تتصل بمسارات OpenCode مباشرة؛ بل تتحدث مستقبلاً إلى بوابة محلية مملوكة لـ Osamah. ثم تستخدم البوابة عميل OpenCode الرسمي من المصدر المستنسخ في `OSAMAH-STUDIO-SOURCES/opencode`.

## المصدر الأصلي الذي يُعاد استخدامه

| نطاق Osamah | واجهة OpenCode المصدرية | الاستخدام المطلوب |
|---|---|---|
| صحة المحرك | `V2HealthGet` | منع ادعاء أن المحرك متصل قبل نجاح فحص الصحة |
| النماذج | `V2ModelList` | استبدال قائمة التفضيلات بالكتالوج الفعلي للمزودين المهيئين |
| المزودون | `V2ProviderList` و`V2ProviderGet` | إظهار قدرة المزود وحالة التهيئة من دون إرسال أسراره للواجهة |
| الجلسات | `V2SessionCreate` و`V2SessionGet` | إنشاء معرّف جلسة محلي لكل سياق محادثة |
| الرسائل | `V2SessionPrompt` و`V2SessionEvents` | تمرير الرسالة وتدفق أحداث الاستجابة الحقيقي |
| التحكم | `V2SessionInterrupt` و`V2SessionSwitchModel` | إيقاف التنفيذ أو تبديل النموذج بعد التحقق من السياسة |

> هذه الأسماء مأخوذة من SDK الإصدار الثاني في OpenCode. ولا تُثبّت البوابة أي مسار HTTP صريح قبل تشغيل SDK الرسمي والتحقق من نسخة المصدر المستخدمة.

## عقد الواجهة إلى البوابة

```ts
type OpenCodeChatEnvelope = {
  message: string;
  context: {
    workspace: "dashboard" | "programming" | "presentations" | "mind" | "settings";
    language: "ar" | "en";
  };
  model: { providerId: string; modelId: string };
};

type OpenCodeModelCatalog = {
  runtime: "unconfigured" | "checking" | "ready" | "degraded" | "offline";
  discoveredAt?: string;
  models: Array<{
    providerId: string;
    modelId: string;
    label: { ar: string; en: string };
    detail: { ar: string; en: string };
    source: "runtime";
  }>;
};
```

تستخدم الواجهة حالياً نفس الأشكال في `client/src/lib/opencode-contract.ts` لكن بعلامة `source: "fallback"`. وتتحول القائمة إلى `runtime` فقط عندما تصل البوابة إلى `V2ModelList` بنجاح.

## تسلسل التنفيذ الحقيقي

1. تفحص البوابة صحة OpenCode عبر `V2HealthGet`.
2. تطلب قائمة النماذج والمزودين وتزيل أي نموذج غير مهيأ أو محظور بالسياسة.
3. تنشئ أو تستعيد جلسة مرتبطة بمساحة العمل وسياق المستخدم.
4. تمرر الرسالة مع زوج `providerID/modelID` الذي اختاره المستخدم.
5. تبث أحداث الجلسة إلى الواجهة وتعرض الحالة الفعلية فقط.
6. تمرر طلبات الصلاحيات والإيقاف إلى واجهات OpenCode الأصلية؛ ولا تمنح تنفيذ الأدوات افتراضياً.

## الحدود الأمنية والتشغيلية

- مفاتيح المزودين تبقى في تهيئة OpenCode أو مخزن أسرار محلي؛ لا تُرسل إلى React أو `localStorage`.
- كل اتصال يلتزم بحلقة محلية أو قناة مصادقة مملوكة للمستخدم عند تجهيز محرك محلي.
- لا يعمل هذا العقد كخدمة دائمة داخل الاستضافة الحالية. تشغيله يحتاج OpenCode مهيأً على جهاز محلي متصل أو بيئة دائمة عند توفرها.
- فشل الصحة أو اكتشاف النماذج يعيد حالة `offline` أو `degraded`؛ لا يتحول إلى رد محاكى.

## الاختبارات المطلوبة قبل الادعاء بالتكامل

| الاختبار | دليل النجاح |
|---|---|
| فحص الصحة | استجابة نجاح فعلية من SDK الرسمي |
| اكتشاف النموذج | نموذج فعلي واحد على الأقل يحمل `providerID/modelID` صالحين |
| دورة جلسة | إنشاء جلسة وإرسال رسالة واستقبال أحداث |
| تبديل النموذج | تسجيل طلب مرفوض أو ناجح وفق مزود مهيأ فعلياً |
| الصلاحيات | طلب صريح قبل تنفيذ أداة حساسة وإدخال نتيجة التدقيق في السجل |
